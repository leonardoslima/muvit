# Ambiente de execução exclusivo por card

1. Garantir repositório correto, acesso ao remoto, branch base remota atualizada e status do Git. Criar branch/worktree curta por card pelo gerenciamento nativo do host, respeitando AGENTS.md e o guia versionado `orca-cli` quando Orca gerenciar o workspace. Não executar `git worktree add` se houver funcionalidade nativa e não duplicar worktree já isolada. Especialistas sequenciais compartilham a worktree do card por seletor exato; não criar outra por papel. Se `worker-start` criar um workspace, seguir o guia Orca em vez de criar checkout manualmente para esse worker. Preservar alterações locais e **não apagar worktree alheia**. Cuidado com caminhos enormes no Windows: preferir diretórios de worktree curtos; use mitigação específica após conferir o problema.
2. Antes de setup, testes ou builds, copiar os arquivos `.env` locais ignorados da raiz original para a worktree, conforme AGENTS.md, sem sobrescrever configuração exclusiva de outra execução. Ajustar portas e recursos para o card. Se a origem não os possuir, usar template/configuração autorizada e registrar ausências necessárias. Worktrees novas não herdam automaticamente ambiente. Garantir a preparação antes de hooks automáticos de setup; usar a política de setup suportada pelo host para manter essa ordem. Não commitar/logar segredos nem incluir arquivos `.env` no briefing ou nos artefatos.
3. Docker deve estar operacional; se instalado mas parado, iniciar conforme acesso disponível. Cada card usa infraestrutura isolada: nomes de projeto/containers, portas, volumes, PostgreSQL e banco próprios. Não usar banco de dev/testes de outro card.
4. Subir **banco e API juntos** antes de testes de integração/E2E ou fluxos de UI dependentes. Verificar migrations, healthchecks e credenciais de seed; executar seeds existentes ou preparar credenciais de teste apropriadas, sem dados reais. API saudável e conectada ao banco fazem parte do gate.
5. Para paralelismo entre cards, separar portas, redes, containers e banco. Se não for possível garantir isolamento, rodadas conflitantes não começam juntas.
6. Executar validação de backend: esquema/migrations, comandos de tests e endpoints reais; o build isolado não substitui checagem de comportamento.
7. Após a entrega concluída e o salvamento das evidências, encerrar os processos e emuladores exclusivos da rodada conforme `closure-and-recovery.md`. Preservar os containers, volumes e dados Docker exclusivos para possíveis correções, sem interromper o Docker compartilhado. Não limpar estado necessário para review pendente ou retomada sem decisão segura. Nunca rodar `git clean`/`git reset` indiscriminadamente.
8. Não atribuir falhas de Docker, rede, dependência ou autenticação à capacidade do modelo. Investigar a causa técnica preservando os perfis fixos; mudanças que invalidem o plano voltam ao planejador.

## Cuidados específicos

- No Windows, build Android/CMake pode falhar com caminhos físicos longos mesmo se aliases com `SUBST` encurtarem o shell; documentar e corrigir na camada de path/toolchain.
- Testes não podem afirmar sucesso usando mock quando a aceitação exige API/DB reais. Se serviço indisponível, marcar `NOT_PROVEN` com motivo.
- Se os recursos não puderem subir por falta de permissão, bloqueio operacional documentado em vez de improvisar credenciais.
