# MUV-14 — Mobile E2E Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Automatizar e executar localmente os fluxos Android de aluno/professor com persistência e isolamento demonstráveis.

**Architecture:** Runner Node nativo cria PostgreSQL/API/Metro exclusivos e invoca fixtures TypeScript no workspace da API e Maestro no AVD confirmado. Fixtures usam HTTP real e acesso DB mínimo para perfil/exercício global. Estado da UI e verificações HTTP independentes compõem o aceite.

**Tech Stack:** Node >=24, pnpm, TypeScript/tsx existente na API, PostgreSQL 16, Drizzle, Better Auth, Expo Go SDK 54, Maestro, Vitest e node:test.

**Spec:** `docs/superpowers/specs/2026-10-21-muv-14-mobile-e2e-design.md`.

## Global Constraints

- Sem nova biblioteca de produto, workflow CI, alteração de schema/contrato, correção de produto ou mudança de UX. Exceção técnica comprovada durante execução: declaração direta do plugin Babel `@babel/plugin-transform-react-jsx@7.28.6`, já presente no lockfile, necessária ao bundle NativeWind.
- Executar da raiz com filtros/cwd explícitos; preservar UTF-8 literal pt-BR.
- Recursos e dados por run/cenário; nunca banco de desenvolvimento, conta compartilhada ou seed demo/R2.
- Android exige serial explícito e AVD exclusivo; padrões API 3344, Metro 8094, DB 5444, AVD desta execução `muvit-muv-14`.
- Evidências em `artifacts/mobile-e2e/<runId>/` por padrão, com `--artifact-scope muv-14` para as evidências desta entrega; senhas/cookies somente em memória e ambiente.
- Aluno usa duas séries `(10 reps, 22 kg)` e `(8 reps, 18 kg)`, volume `364 kg`; professor altera carga de 20 para 24 kg.
- Processos/containers próprios são limpos em `finally`; AVD externo e artefatos são preservados.
- Execução e revisão independentes são coordenadas pelo executor; este plano não delega commit/push/Linear ao implementador especializado.

## Review Focus

- Falha parcial depois de criar banco/API deve limpar somente recursos criados pelo run (tarefa 1).
- Auth user ID confundido com perfil ou catálogo privado usado como global invalida a fixture (tarefa 1).
- Reabertura com `clearState` esconde persistência e troca de identidade; usá-lo só no primeiro login do cenário (tarefas 2/3/4).
- HTTP 200 ou mensagem offline não comprovam os valores persistidos; comparar conteúdo e quantidade de registros (tarefas 2/3).
- Tentativa cruzada de escrita pode falhar visualmente mas alterar dados; conferir novamente com o dono após negação (tarefa 4).
