# Release v0.2.0-beta.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publicar `v0.2.0-beta.1` como GitHub prerelease a partir do estado validado de `develop`, promovido integralmente para `main`.

**Architecture:** A preparação altera somente o metadado de versão raiz e o changelog. A promoção ocorre por PR `develop → main`, validada pelo CI atual; depois do merge, uma tag anotada fixa o commit de `main`, a GitHub Release é publicada e a branch recebe proteção baseada nos três checks existentes.

**Tech Stack:** Git, GitHub CLI, GitHub Actions, pnpm 10 via Corepack, Turborepo, Biome, TypeScript e Vitest.

## Global Constraints

- A versão publicada deve ser exatamente `0.2.0-beta.1` e a tag deve ser `v0.2.0-beta.1`.
- A GitHub Release deve ser marcada como prerelease.
- A checklist de soft-launch permanece aberta e não pode ser apresentada como concluída.
- Nenhuma branch de dependências, atualização de pacote ou migração de gerenciador entra nesta entrega.
- As versões internas `0.0.0` dos workspaces privados permanecem inalteradas.
- O histórico de `develop` deve ser preservado por merge normal, sem squash, rebase ou force-push.
- A tag e a release só podem ser criadas depois de CI verde e merge confirmado em `main`.
- Textos pt-BR devem permanecer em UTF-8 literal, sem escapes Unicode para acentuação.

## Agent Routing

A execução deve usar `superpowers:subagent-driven-development`, com um implementer novo e um reviewer separado para cada task. Todos os agents devem ser criados com `fork_turns: "none"` e receber somente o brief, os artefatos de execução e o contexto estritamente necessário.

As tasks são sequenciais. Elas não podem ser executadas em paralelo porque compartilham o mesmo histórico Git e dependem do estado externo produzido pela etapa anterior no GitHub.

| Task | Complexidade | Implementer | Esforço | Reviewer | Esforço | Evidência principal |
|---|---|---|---|---|---|---|
| 1. Metadados e changelog | Baixa | `gpt-5.6-terra` | `medium` | `gpt-5.6-terra` | `medium` | Especificação quase transcritiva, dois arquivos funcionais e escopo fechado |
| 2. Verificação local | Média | `gpt-5.6-terra` | `high` | `gpt-5.6-terra` | `high` | Vários comandos, Docker, PostgreSQL e todos os workspaces |
| 3. Push e PR | Média | `gpt-5.6-terra` | `high` | `gpt-5.6-sol` | `medium` | Mutação externa reversível que exige conferir refs, escopo e metadados |
| 4. CI e merge | Alta | `gpt-5.6-sol` | `high` | `gpt-5.6-sol` | `high` | Promoção de alto impacto e interpretação correta dos checks |
| 5. Tag e prerelease | Muito alta | `gpt-5.6-sol` | `xhigh` | `gpt-5.6-sol` | `xhigh` | Tag pública e release são difíceis de corrigir sem ruído histórico |
| 6. Proteção e auditoria | Muito alta | `gpt-5.6-sol` | `xhigh` | `gpt-5.6-sol` | `xhigh` | Configuração incorreta pode bloquear merges ou deixar `main` desprotegida |

### Escalonamento

- Fix rounds 1–3 retomam o implementer original com o mesmo modelo e esforço.
- Nas Tasks 1–3, fix rounds 4–5 usam um implementer novo com `gpt-5.6-sol` e esforço `high`.
- Nas Tasks 4–6, fix rounds 4–5 usam um implementer novo com `gpt-5.6-sol` e esforço `max`.
- Scoped re-reviews usam o mesmo modelo e esforço do reviewer original da task.
- A revisão final de toda a entrega usa `gpt-5.6-sol` com esforço `max`.
- `ultra` não deve ser usado: o plano não contém arquitetura inédita, debugging extremo ou ambiguidade suficiente para justificar esse custo.

```markdown
- Aplicação de fronteiras SOLID na API, web e mobile, com casos de uso e repositórios isolados.
- Ampliação dos testes e dos pisos de cobertura funcional, visual e arquitetural.
- Atualização do dashboard para Next.js 16, React 19 e Tailwind CSS 4.
- Separação segura do banco de integração e melhoria do seed de demonstração.
- Inicialização coordenada da API junto do dashboard no fluxo local de desenvolvimento.

### Operação

- Documentação de ambientes por workspace, banco de testes, backup e checklist de soft-launch.
- CI com Biome, build do monorepo e verificação TypeScript.
- A prontidão para produção continua acompanhada separadamente em `docs/operations/launch-checklist.md`.

[0.2.0-beta.1]: https://github.com/leonardoslima/muvit/compare/v0.1.0-mvp...v0.2.0-beta.1
```

### Task 4: Aguardar CI e promover para main

**Files:**
- Verify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: PR criada na Task 3.
- Produces: `main` contendo todo o histórico de `develop` por merge normal.

- [ ] **Step 3: Fazer merge normal**

Run:

### Task 5: Criar tag anotada e GitHub prerelease

**Files:**
- Read: `CHANGELOG.md`

**Interfaces:**
- Consumes: HEAD remoto de `main` confirmado na Task 4.
- Produces: tag anotada `v0.2.0-beta.1` e GitHub prerelease publicada.

- [ ] **Step 1: Garantir que a tag ainda não existe**

Run:

```powershell
git tag --list v0.2.0-beta.1
gh api repos/leonardoslima/muvit/git/ref/tags/v0.2.0-beta.1
```

Expected: nenhuma tag local ou remota existente. Uma resposta `404` da API é o resultado esperado antes da criação.

- [ ] **Step 2: Criar e publicar a tag anotada**

Run:

```powershell
git tag -a v0.2.0-beta.1 origin/main -m "Muvit v0.2.0-beta.1"
git show --no-patch --format=fuller v0.2.0-beta.1
git push origin v0.2.0-beta.1
```

Expected: tag anotada apontando exatamente para o commit promovido em `origin/main`.

- [ ] **Step 3: Publicar a GitHub prerelease**

Run:

```powershell
$releaseBody = Get-Content -Raw -Encoding utf8 CHANGELOG.md
$releasePayload = @{
  tag_name = 'v0.2.0-beta.1'
  target_commitish = 'main'
  name = 'Muvit v0.2.0-beta.1'
  body = $releaseBody
  draft = $false
  prerelease = $true
} | ConvertTo-Json -Depth 4
$releasePayload | gh api --method POST repos/leonardoslima/muvit/releases --input -
```

Expected: resposta com `tag_name: v0.2.0-beta.1`, `draft: false`, `prerelease: true` e URL pública.

### Task 6: Proteger main e auditar o resultado final

**Files:**
- Verify: `.github/workflows/ci.yml`
- Verify: `docs/operations/launch-checklist.md`

**Interfaces:**
- Consumes: nomes dos checks atuais e prerelease publicada.

- [ ] **Step 1: Configurar proteção baseada no CI**

Run:

```powershell
$protectionPayload = @{
  required_status_checks = @{
    strict = $true
    contexts = @('Check (Biome)', 'Build (Turborepo)', 'TypeScript Check')
  }
  enforce_admins = $true
  required_pull_request_reviews = $null
  restrictions = $null
} | ConvertTo-Json -Depth 5
$protectionPayload | gh api --method PUT repos/leonardoslima/muvit/branches/main/protection --input -
```

Expected: proteção ativa em `main`, exigindo os três checks e aplicada também a administradores.

- [ ] **Step 2: Verificar tag, release e proteção**

Run:

```powershell

git rev-parse 'v0.2.0-beta.1^{}'
```

Expected: release pública e marcada como prerelease, proteção ativa e commit resolvido da tag idêntico a `origin/main`.
