# Release v0.2.0-beta.1

**Data:** 2026-07-30

## Contexto

O Muvit possui somente a tag leve `v0.1.0-mvp`, criada em 19 de maio de 2026, e nenhuma GitHub Release publicada. Desde esse marco, `develop` acumulou mudanças relevantes de produto, arquitetura, autenticação, testes e dependências, enquanto `main` permaneceu desatualizada.

O código versionado e o lançamento público são marcos diferentes. A checklist de soft-launch ainda contém pendências operacionais, mas isso não impede a publicação de uma prerelease técnica que registre o estado atual do código.

## Objetivo

Publicar `v0.2.0-beta.1` como a primeira GitHub prerelease formal do Muvit, promovendo o estado validado de `develop` para `main` e registrando as mudanças acumuladas desde `v0.1.0-mvp`.

## Escopo

- Atualizar a versão do pacote raiz de `0.1.0` para `0.2.0-beta.1`.
- Criar um `CHANGELOG.md` com as mudanças relevantes desde `v0.1.0-mvp`.
- Publicar a preparação da versão em `develop`.
- Abrir uma PR de promoção de `develop` para `main`.
- Exigir CI verde antes do merge.
- Fazer o merge sem reescrever o histórico de `develop`.
- Criar a tag anotada `v0.2.0-beta.1` no commit promovido para `main`.
- Publicar uma GitHub Release marcada como prerelease.
- Proteger `main` contra atualizações diretas sem os checks de CI configurados.

## Fora de escopo

- Declarar o Muvit pronto para soft-launch ou produção.
- Concluir os itens de infraestrutura, domínio, deploy, backup, observabilidade ou lojas mobile.
- Incluir mudanças ainda não integradas de branches de dependências.
- Atualizar dependências ou migrar o gerenciador de pacotes.
- Criar releases retroativas para marcos intermediários.
- Alterar versões internas `0.0.0` dos workspaces privados.

## Estratégia de versionamento

O número `0.2.0-beta.1` comunica três fatos:

- o conjunto de mudanças é maior que um patch sobre `0.1.0`;
- o projeto continua anterior a `1.0.0`;
- a versão registra um marco técnico, mas não afirma prontidão operacional para usuários reais.

As próximas correções compatíveis poderão usar `v0.2.0-beta.2`. Quando os critérios técnicos e operacionais definidos para esse ciclo forem cumpridos, a série poderá avançar para `v0.2.0`.

## Fluxo de promoção

1. Preparar versão e changelog em `develop`, sem misturar trabalho de outras branches.
2. Executar verificações locais relevantes e pesquisar escapes Unicode indevidos nos arquivos textuais alterados.
3. Publicar `develop` e abrir uma PR pronta para revisão contra `main`.
4. Aguardar os jobs `Check (Biome)`, `Build (Turborepo)` e `TypeScript Check`.
5. Fazer o merge somente com todos os jobs concluídos com sucesso.
6. Confirmar que o commit promovido é o HEAD de `main`.
7. Criar a tag e a GitHub prerelease a partir desse commit.
8. Configurar proteção de `main` com os checks de CI como requisitos.

## Changelog

O changelog será curado por impacto, não uma cópia integral do `git log`. Ele destacará:

- migração da autenticação própria para Better Auth;
- evolução do dashboard, detalhe do estudante e fluxos web;
- aplicação de fronteiras SOLID na API, web e mobile;
- ampliação de testes e pisos de cobertura;
- modernização do web para Next.js 16 e Tailwind CSS 4;
- melhorias no banco de testes, seed de demonstração e documentação operacional;
- atualização do fluxo local para iniciar a API junto do dashboard.

As release notes do GitHub reutilizarão esse resumo e incluirão o comparativo completo com `v0.1.0-mvp`.

## Verificação e falhas

- Qualquer falha local ou de CI interrompe a promoção.
- Se a PR revelar conflito entre `develop` e `main`, o conflito será resolvido em uma branch dedicada e revalidado, sem force-push.
- A tag e a GitHub Release só serão criadas depois que o merge estiver confirmado em `main`.
- Se a configuração de proteção de branch não estiver disponível no plano atual do GitHub, a release poderá ser concluída, mas a limitação será registrada explicitamente.

## Critérios de aceite

- `main` contém integralmente o estado versionado de `develop` usado na preparação.
- A versão raiz é `0.2.0-beta.1`.
- O changelog descreve o intervalo desde `v0.1.0-mvp`.
- Todos os checks exigidos passam no commit promovido.
- A tag `v0.2.0-beta.1` aponta para o HEAD publicado de `main`.
- A GitHub Release está publicada e marcada como prerelease.
- A checklist de soft-launch permanece aberta e não é apresentada como concluída.
